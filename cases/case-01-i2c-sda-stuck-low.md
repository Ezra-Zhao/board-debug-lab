# Case 01 — I2C bus scan fails: every address NACKs, SDA stuck low

> Status: **method / framework demonstration with synthetic data.**
> This is not a record of a real board repair. No oscilloscope or logic
> analyzer capture exists for this case yet — see "Honest boundary" below.
> The waveform in this file is generated by a Python script, labelled
> synthetic everywhere it appears, and is used to show *how the waveform
> would be read*, not to claim a measurement was taken.

Related tool output (also synthetic): `samples/synthetic_test_run.log`
lines 7–8 — `i2c_scan FAIL code=ERR_I2C_NACK` at two addresses in a row.
A single-address NACK can be a missing device; *every* address NACKing
points first at the bus itself, not at one peripheral. That pattern is
what starts this case.

## 1. Phenomenon

- Test step: I2C bus scan during board bring-up.
- Symptom (synthetic scenario): scan returns NACK for every probed
  address, including addresses that should ACK.
- Controller does not report a bus-busy timeout before the transfer; the
  failure appears per-transaction, which makes "one dead peripheral"
  and "bus held by something" the two competing first hypotheses.
- What is *not* assumed: that the peripheral at 0x50 is faulty. Jumping
  to replacing that part is the classic wrong first move on a bus fault.

## 2. Measurement

Measurement plan — the order matters, cheapest and least invasive first:

1. **Static levels, no traffic (multimeter / scope, DC):** measure SDA
   and SCL idle levels against the rail. Expected: both pulled up to the
   rail when idle. A data line sitting at ~0 V idle is already a result,
   before any protocol decoding.
2. **Dynamic capture (logic analyzer or scope, 2 channels minimum):**
   trigger on the START condition, capture SCL + SDA for one full frame
   (8 data clocks + ACK clock).
3. **Resistance check, power off:** SDA-to-GND resistance compared with
   SCL-to-GND and with a known-good identical bus if one exists on the
   board. A hard short and a device holding the line read differently.
4. **Isolation:** if the design allows it, lift / depopulate bus members
   one at a time (or cut a series element / use a solder jumper where the
   schematic provides one) and re-check the idle level after each step.

Files:

  (241 time rows + header; columns `time_us,scl,expected_sda,observed_sda_stuck_low`)
- Plot: `../data/waveforms/case01_i2c_waveform.png`
- Generator: `../tools/generate_waveforms.py` — re-run it to reproduce
  both files exactly.

How to read the synthetic plot, top to bottom:

- **SCL (top):** nine clean clock pulses after the frame start. The
  controller side is clocking normally, so "controller never tried" is
  ruled out in this scenario.
- **SDA expected (middle):** the trace a healthy frame would show for
  the invented byte `0xA0` — data bits change only while SCL is low,
  and the receiver pulls SDA low in the 9th (ACK) slot, then releases.
- **SDA observed (bottom):** falls at the START edge and **never comes
  back up**. Data bits are unreadable, and the ACK slot is
  *indistinguishable* from the rest of the frame.

The diagnostic sentence this waveform supports — and the only one it
supports — is: "SDA is being held low independently of the intended data;
the fault is in whatever can pull SDA down (a short, a damaged device
output, a solder bridge, or a device stuck mid-transaction), not in the
data content and not in SCL generation." It does **not** identify which
device. That takes the isolation step in the measurement plan, not a
prettier waveform.

## 3. Localization

Decision chain, in the order it narrows the fault:

1. SCL clocks + SDA stuck → fault is on the SDA net or a device on it.
2. Idle SDA low with no traffic → not a protocol / addressing error;
   something holds the line electrically, or a device is wedged in a
   state where it drives SDA.
3. Bus recovery attempt (clock SCL up to 9 pulses with SDA released, a
   standard recovery sequence): if SDA frees, a device was stuck
   mid-byte; if it does not, suspect a hard electrical fault.
4. Isolate members one at a time, re-measuring idle SDA after each:
   the step where the line releases names the segment / device.
5. Inspect that segment under magnification before touching the iron:
   solder bridge between adjacent pins, a tombstoned or shifted part
   shorting the net, or visible damage. Schematic + layout: confirm
   which pads belong to the SDA net before declaring a bridge.

## 4. Fix

Fix follows the isolated cause — the framework lists the branches, it
does not pick one in advance:

- Solder bridge → remove with wick / hot air, clean flux, re-inspect.
- Damaged device holding the bus → replace that device only, after the
  isolation step has actually named it.
- Device wedged mid-transaction (recovers with bus-clear) → no rework;
  the fix is in sequencing / reset handling, and the case becomes a
  power-up ordering note, not a solder note.
- In every branch: no "replace parts until it works". Each swap without
  an isolation result destroys the evidence the next step needs.

## 5. Verification

- Idle SDA and SCL both at rail level with no traffic.
- Bus scan ACKs the expected address set — and only that set.
- Repeat the failing test step from the log (`i2c_scan`) plus a sustained
  transfer test, not a single transaction: an intermittent holder passes
  one frame and fails the hundredth.
- Cold boot re-test: a fault that only appears on warm restart is a
  different case and must not be closed by a warm-boot pass.

## Honest boundary

- The scenario, log lines, and waveform are **synthetic / invented for
  this lab**. They demonstrate a debug *method*: symptom pattern →
  ordered measurements → isolation → cause-matched fix → regression
  verification.
- **Not yet done:** a real capture on a real board with a real scope or
  logic analyzer, real measured voltages / timings, and a real rework
  record. Those require physical hardware and test equipment and are
  explicitly future work. Nothing in this case should be cited as
  hands-on instrument experience.
